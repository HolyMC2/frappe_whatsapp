# WhatsApp Account Health — 2026-09-10

Implemented the saved Account → Health dialog → local evidence or explicit phone check → scoped receipt list or Customer Conversations path. No schema, account controller, webhook or transport changes. All changes remain git-unstaged; no commits, migration, production calls, subscription changes or customer sends.

`frappe_whatsapp.account_health.get_health(account_name, expected_modified)` reads local metadata only. `check_phone(account_name, expected_modified)` is the separate POST-only broker for an ephemeral provider GET. Both require a current enabled System Manager (including Frappe's built-in Administrator), current locked User/Has Role rows, current locked saved WhatsApp Account, read permission and matching modified revision. Caller-supplied account documents, URLs, tokens and field lists are not inputs. Current authority/account locks cover the bounded check; no snapshot role cache grants access. This serializes concurrent changes to the inspected manager/account until the request finishes.

Local output contains configured/missing/invalid states for token, App Secret, App/WABA/Phone IDs, verification token and Graph version. Credential presence is queried as encrypted field names; opening Health never decrypts them. Phone and WABA receipts have separate exact provider/account/app aggregate counts and last-received dates. Native outbound intent counts are exact provider/phone and explicitly distinguish `Unknown`. Optional missing core/ledger data is unavailable, never zero-success evidence. SQL never selects message bodies, receipt payloads, event IDs or recipient addresses. Credential values and provider error text are never projected.

At most ten known quality/account/template WABA receipt observations are returned with received date, receipt state and signed-receipt source. They are labelled unsupported/order-unverified and phone mapping unverified. No payload parsing, arrival-order quality folding or guessed WABA-to-phone attribution occurs. Meta's [quality webhook example](https://www.postman.com/meta/whatsapp-business-platform/request/zxa0yi6/phone-number-quality-update-received) carries a display number, not this schema's Phone ID, so it cannot establish current phone quality here.

The explicit check uses only stored Phone ID, validated Graph version and that named account's token: `GET https://graph.facebook.com/{version}/{phone_id}?fields=id,quality_rating` through the existing `transport.raw`, Bearer header, redirects disabled, 5/10-second connect/read timeouts, a 20-second checked stream deadline and 64 KiB response cap. Individual socket reads remain subject to their own timeout. Duplicate JSON keys, nonfinite JSON, wrong ID, unexpected fields/quality enum, oversized or invalid streams fail closed. Demo/inactive/missing configuration blocks before transport; Demo never returns fake connected evidence. Authentication, permission, rate-limit and unavailable results remain distinct and sanitized. No retries, writes, commits or logging of provider content occur.

Meta's official [Get Phone Number By ID](https://www.postman.com/meta/whatsapp-business-platform/request/li0unxe/get-phone-number-by-id) fixes the host and object path. Its [Cloud API documentation](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api?entity=request-13382743-5a8389e6-5e86-48e6-85da-577d6e8d4474) documents Bearer authentication and `id`/`quality_rating`, including GREEN/YELLOW/RED/NA. Successful output carries `checked_at`, `source=meta_graph_phone_get`, `scope=phone_metadata_only` and `persisted=false`. Subscription and end-to-end webhook-delivery state stay unknown. Missing webhook App/secret configuration remains visible even if the independent phone metadata GET succeeds.
